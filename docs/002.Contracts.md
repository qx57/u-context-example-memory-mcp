# Контракты MCP и REST

## Операции

Spring использует одни DTO и прикладные операции для REST и MCP. В JSON используются имена в `camelCase`. Ключевые поля хранилища и служебные параметры Mem0 остаются внутри адаптера.

| MCP-инструмент | REST | Результат |
|---|---|---|
| `record_test_observation` | `PUT /api/v1/memories/{observationId}` | `200` и квитанция записи. MCP принимает `observationId` в аргументах |
| `search_test_observations` | `POST /api/v1/memories/search` | `200` и ранжированный список наблюдений |
| — | `GET /api/v1/memories` | `200` и страница записей для оператора |
| — | `GET /api/v1/memories/{observationId}` | `200`, карточка записи и `ETag` текущей ревизии |
| — | `PATCH /api/v1/memories/{observationId}` | `200`, обновлённая карточка и новый `ETag` |

Для MCP запись объявляется с `idempotentHint=true`, поиск — с `readOnlyHint=true`. Оба инструмента объявляют входную и выходную схемы. Успех возвращается как `structuredContent` и продублированный JSON в текстовом блоке для совместимости. Ошибки выполнения возвращаются с `isError=true` и сериализованным объектом ошибки в текстовом блоке. Ошибки протокола обрабатывает MCP SDK. [Спецификация инструментов MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

Для REST используется отдельный локальный токен оператора в `Authorization: Bearer`. В браузере оператор входит в интерфейс `/ui/memories` и получает сессию. Изменяющие действия интерфейса требуют CSRF-токен. Страницы интерфейса вызывают прикладные операции напрямую внутри Spring.

## Запись наблюдения

Пример аргументов `record_test_observation`. В REST `observationId` передаётся в пути, остальные поля — в теле.

```json
{
  "observationId": "020bc850-096f-4793-8ad5-dba9b12df958",
  "serviceId": "catalog",
  "environment": "local",
  "runId": "run-42",
  "testCaseId": "missing-item",
  "method": "GET",
  "route": "/items/{id}",
  "observedAt": "2026-11-23T08:30:00Z",
  "task": "Проверить чтение отсутствующей позиции каталога",
  "approach": "Запросить позицию с идентификатором из пустой тестовой фикстуры",
  "evidence": {
    "executionStatus": "COMPLETED",
    "passedAssertions": 2,
    "failedAssertions": 0,
    "expected": "HTTP 404 и код ITEM_NOT_FOUND",
    "observed": "HTTP 404 и код ITEM_NOT_FOUND",
    "reportRef": "catalog-suite/run-42/missing-item"
  }
}
```

- `observationId` — UUID, назначенный вызывающей стороной один раз на попытку. При повторной передаче клиент сохраняет UUID и входные данные. Различающиеся данные с тем же UUID дают `IDEMPOTENCY_CONFLICT`.
- `serviceId`, `environment`, `runId` и `testCaseId` — обязательные идентификаторы длиной до 128 символов. Допустимы латиница, цифры и разделители `.`, `_`, `-`. Идентификаторы чувствительны к регистру.
- `method` — один из `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`. `route` — локальный шаблон пути до 256 символов, начинающийся с `/`. Параметры запроса, фрагменты, полный URL и значения, подставленные вместо шаблонных параметров, исключаются из контракта.
- `observedAt` — время завершения попытки в RFC 3339. Для `NOT_RUN` это время фиксации пропуска. `createdAt` устанавливается сервером.
- `task` и `approach` — краткие непустые строки до 1000 символов каждая. `evidence.expected` обязателен и ограничен 500 символами. `evidence.observed` обязателен для `COMPLETED` и ограничен 500 символами. `reportRef` — необязательный непрозрачный идентификатор отчёта длиной до 256 символов. Допустимы латиница, цифры и разделители `.`, `_`, `:`, `/`, `-`. По нему оператор может найти отчёт в системе раннера.
- `executionStatus` принимает `COMPLETED`, `NOT_RUN`, `INFRA_ERROR` и `TIMEOUT`. Счётчики `passedAssertions` и `failedAssertions` обязательны для `COMPLETED` и являются целыми числами от 0 до 10 000. Для остальных статусов оба поля опускаются.
- Неизвестные поля входных DTO отклоняются. Проверка очистки применяется к записи, поисковой фразе и комментарию оператора. Произвольный payload и параметры Qdrant извне недоступны.

| Условие | `autoOutcome` |
|---|---|
| `COMPLETED` и `failedAssertions > 0` | `FAILED` |
| `COMPLETED`, `failedAssertions = 0` и `passedAssertions > 0` | `SUCCEEDED` |
| Все остальные допустимые комбинации | `INCONCLUSIVE` |

Сервис рассчитывает автоматический исход по полям отчёта. Доступ к первичным отчётам остаётся у оператора. `effectiveOutcome` равен ручной оценке при её наличии и `autoOutcome` в остальных случаях. Новая запись начинает с `status=ACTIVE`, `revision=1` и `manualReview=null`.

Успешная запись и повтор с тем же входом возвращают одинаковую квитанцию.

```json
{
  "observationId": "020bc850-096f-4793-8ad5-dba9b12df958",
  "createdAt": "2026-11-23T08:30:02Z"
}
```

## Поиск памяти

```json
{
  "serviceId": "catalog",
  "environment": "local",
  "query": "Как проверить отсутствующую позицию в каталоге?",
  "method": "GET",
  "route": "/items/{id}",
  "outcomes": ["SUCCEEDED", "FAILED"],
  "limit": 5
}
```

`serviceId`, `environment` и непустой `query` длиной до 1000 символов обязательны. `method` и `route` — необязательные точные фильтры. `outcomes` по умолчанию включает `SUCCEEDED` и `FAILED`, а `INCONCLUSIVE` можно запросить явно. Если `outcomes` передан, он содержит от одного до трёх уникальных допустимых значений. `limit` принимает значения от 1 до 20, по умолчанию 5. Все MCP- и REST-запросы семантического поиска ограничены статусом `ACTIVE`.

```json
{
  "items": [
    {
      "observationId": "020bc850-096f-4793-8ad5-dba9b12df958",
      "observedAt": "2026-11-23T08:30:00Z",
      "method": "GET",
      "route": "/items/{id}",
      "task": "Проверить чтение отсутствующей позиции каталога",
      "approach": "Запросить позицию с идентификатором из пустой тестовой фикстуры",
      "expected": "HTTP 404 и код ITEM_NOT_FOUND",
      "observed": "HTTP 404 и код ITEM_NOT_FOUND",
      "effectiveOutcome": "SUCCEEDED",
      "outcomeSource": "AUTO",
      "score": 0.82
    }
  ]
}
```

При отсутствии наблюдаемого результата поле `observed` имеет значение `null`. `outcomeSource` принимает `AUTO` или `MANUAL`. Результаты упорядочены по убыванию релевантности. `score` — оценка ранжирования Mem0. Пустая выдача возвращается как `{"items":[]}` только после выполненного поиска. Для сопоставления успешной и неудачной попыток агент может вызвать поиск отдельно по каждому исходу.

## Интерфейс оператора

Список `GET /api/v1/memories` принимает необязательные точные `serviceId`, `environment`, `runId`, `outcome` и `status`. `status` принимает `ACTIVE` по умолчанию или `ARCHIVED`. Размер страницы `limit` от 1 до 100, по умолчанию 25. `cursor` берётся из `nextCursor` предыдущей страницы вместе с теми же фильтрами. Ответ содержит `items` и `nextCursor`, где `null` обозначает последнюю страницу. Элементы списка содержат `observationId`, `serviceId`, `environment`, `runId`, `testCaseId`, `method`, `route`, `observedAt`, `task`, `effectiveOutcome`, `outcomeSource` и `status`.

Карточка по `observationId` возвращает поля исходной записи после очистки, `createdAt`, `updatedAt`, `autoOutcome`, `manualReview`, `effectiveOutcome`, `status` и `revision`. Интерфейс показывает сохранённое доказательство и помечает источник текущей оценки. Список и карточка используют выборку Qdrant без вычисления эмбеддингов.

Для `PATCH` требуется `If-Match` с текущим `ETag`, например `If-Match: "1"`. Пример назначения ручной оценки.

```json
{
  "manualReview": {
    "verdict": "INCONCLUSIVE",
    "reason": "После прогона выяснилось, что фикстура каталога не была изолирована"
  }
}
```

Допустимые значения `verdict` совпадают с исходами. `reason` обязателен и ограничен 500 символами. В сохранённый `manualReview` сервер добавляет `reviewedAt` и `reviewerId` из аутентификации. `{"manualReview":null}` снимает ручную оценку. `{"status":"ARCHIVED"}` архивирует запись, `{"status":"ACTIVE"}` восстанавливает её. Запрос содержит минимум одно из изменяемых полей, пропущенные поля сохраняют прежние значения. Интерфейс показывает карточку после правки или предлагает перечитать её при конфликте ревизий.

## Ошибки и повторные вызовы

Форма прикладной ошибки одинакова для HTTP JSON и текстового JSON в результате MCP. Пример `{"code":"IDEMPOTENCY_CONFLICT","message":"UUID уже связан с другим наблюдением","retryable":false,"requestId":"req-42"}`.

| HTTP | Код | Действие клиента |
|---|---|---|
| `400` | `INVALID_INPUT` | Исправить данные по контракту |
| `400` | `SENSITIVE_INPUT` | Убрать конфиденциальные данные и повторить |
| `401` | `UNAUTHENTICATED` | Предъявить учётные данные оператора |
| `403` | `FORBIDDEN` | Проверить разрешения и настройки браузерной сессии |
| `404` | `MEMORY_NOT_FOUND` | Проверить UUID |
| `409` | `IDEMPOTENCY_CONFLICT` | Проверить вход или использовать UUID новой попытки |
| `412` | `REVISION_CONFLICT` | Перечитать запись перед правкой |
| `428` | `REVISION_REQUIRED` | Получить `ETag` карточки и передать `If-Match` |
| `429` | `BUSY` | Повторить с задержкой |
| `503` | `DEPENDENCY_UNAVAILABLE` | Проверить состояние зависимости. Повтор записи выполняется с тем же UUID, перед повтором правки нужно перечитать карточку |
| `503` | `CONFIGURATION_ERROR` | Проверить настройки и совместимость провайдера, коллекции и Mem0 |

`retryable=true` у `BUSY` и `DEPENDENCY_UNAVAILABLE` означает, что повтор возможен с соблюдением контракта операции. Сообщения исключают тела запросов, ключи и ответы провайдера. Тайм-аут записи оставляет неопределённый для клиента результат до повторного чтения или повтора с тем же UUID.
